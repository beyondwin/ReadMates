# 호스트 모임 작업 전체 과정 회고

작성일: 2026-08-26

기준 커밋: 기능 브랜치 `bfba21ea`, 로컬 `main` 머지 `3cb70a20`

문서 성격: 작업 방식 개선을 위한 시점별 회고. 현재 제품 동작의 기준은 코드와 [`docs/development/architecture.md`](../development/architecture.md)다.

ADR 영향: `none`. 제품 계약이나 아키텍처 결정을 새로 만들지 않는다.

## 1. 한눈에 보는 결론

기능 자체는 필요한 안전장치와 검증을 갖추고 `main`에 머지됐다. 다만 작업 과정은 예상보다 길어졌고, 후반부에 통합 비용이 크게 몰렸다.

가장 먼저 개선할 세 가지는 다음과 같다.

1. **병렬 작업의 겹치는 파일을 시작 전에 정한다.** 특히 DB 변경 파일, 공통 API 계약, ADR 인덱스는 한 작업자만 최종 편집한다.
2. **큰 통합을 마지막까지 미루지 않는다.** 기능 묶음 하나가 끝날 때마다 최신 `main`과 합쳐 보고, 충돌과 계약 차이를 일찍 발견한다.
3. **검증 결과를 커밋과 함께 보관한다.** 코드가 바뀌지 않은 영역은 같은 전체 검사를 다시 돌리지 않고, 실제로 다시 바뀐 범위만 확인한다.

| 문제 | 이번 작업에서 생긴 영향 | 다음 작업의 기본 규칙 |
| --- | --- | --- |
| 수정 라운드가 계속 늘어남 | 같은 위험을 다른 표현으로 반복 검토 | 세 번째 라운드 전에 범위와 종료 기준을 다시 정한다 |
| 기능 브랜치가 너무 커짐 | 마지막 머지가 228개 파일을 다룸 | 기능 묶음별 통합 지점을 만든다 |
| 병렬 작업 범위가 겹침 | API, DB 변경, 문서에서 충돌 발생 | 시작 전에 파일 소유자 표를 만든다 |
| 전체 검사를 자주 반복 | 이미 확인한 영역까지 다시 기다림 | 커밋별 검증 기록을 재사용한다 |
| 테스트 도우미가 화면 변경을 늦게 따라감 | 실제 기능보다 E2E 수정이 뒤늦게 몰림 | 화면과 E2E 도우미를 같은 작업 단위로 고친다 |
| 일부 테스트가 실행 순서에 민감함 | 전체 실행에서만 일시 실패 | 단독 재현으로 실제 회귀와 흔들림을 먼저 구분한다 |
| 아키텍처 검사가 파일 모양에 의존함 | 안전한 파일 분리도 허용 목록을 깨뜨림 | 파일명보다 동작 규칙을 검사한다 |
| 기존 문서 변경이 `main`에 남아 있었음 | 머지 뒤 복원 과정에서 문서 충돌 | 시작 시 변경 파일 목록과 복원 방법을 기록한다 |

## 2. 확인된 사실

이 회고는 느낌이 아니라 저장소 기록을 기준으로 작성했다.

- 기능 브랜치는 기존 `main` 기준점 `8c0de632` 이후 23개 커밋으로 닫혔다.
- 머지 커밋은 228개 파일, 12,429줄 추가, 2,168줄 삭제를 포함했다.
- 작업 보고서에 명시된 수정 라운드는 A7 4회, B3 3회, B4 2회, B5 2회로 최소 11회다.
- 일부 작업은 `DONE_WITH_CONCERNS`로 끝났고, 남은 문제가 뒤 작업의 통합 단계로 넘어갔다.
- 기능 브랜치와 당시 `main`에는 같은 이름의 `V54`, `V55` DB 변경 파일이 있었지만 내용이 달랐다. 최종 머지에서는 이미 적용된 `main` 쪽을 기준으로 정리했다.
- 최종 통합에서 보안 테스트용 빈 누락, DB 조회 허용 목록, convergence 포트 메서드 목록처럼 각 브랜치에서는 보이지 않던 문제가 발견됐다.
- 전체 서버 검사에서 AI 스케줄러 로그 검증 1건이 일시 실패했지만, 해당 테스트 묶음만 다시 실행했을 때 4건 모두 통과했다.

이 수치는 코드 품질이 낮다는 뜻이 아니다. **작업 단위를 나누는 방식과 통합 시점이 비효율적이었다는 증거**다.

## 3. 비효율적이었던 부분

### 3.1 수정 라운드의 종료 조건이 늦게 정해졌다

초기에는 각 리뷰에서 발견된 항목을 모두 닫는 방식으로 진행했다. 한 항목을 고치면 더 세밀한 증명을 요구하는 새 항목이 생겼고, 실제 장애 가능성이 낮은 검증 공백도 다음 라운드로 이어졌다.

문제점:

- 중요한 결함과 낮은 가능성의 보완 항목이 같은 우선순위로 취급됐다.
- 이미 통과한 검증도 “혹시 모르니” 다시 실행하는 일이 생겼다.
- 기능 완성보다 형식적 증명을 늘리는 데 시간이 많이 들었다.

개선:

- 시작할 때 `반드시 닫을 위험`과 `남은 위험으로 기록할 항목`을 구분한다.
- 개인정보 노출, 데이터 손실·오염, 실제 교착 상태, 인증·권한 우회, 빌드·테스트 실패만 새 수정 라운드의 기본 조건으로 삼는다.
- 세 번째 수정 라운드가 필요해지면 코드를 바로 고치지 말고, 같은 원인을 여러 테스트가 반복해서 표현하는지 먼저 확인한다.

### 3.2 병렬 작업의 경계가 충분히 좁지 않았다

호스트 모임 화면 작업과 platform-admin/public convergence 작업이 동시에 진행되면서 공통 서버 코드, API 계약, DB 변경 파일, 문서 인덱스가 겹쳤다.

문제점:

- 각 브랜치에서는 맞던 코드가 합쳐진 뒤 서로 다른 계약을 기대했다.
- 같은 번호의 DB 변경 파일이 서로 다른 내용으로 존재했다.
- 기능과 직접 관련이 적은 admin 화면까지 호스트 기능 브랜치의 머지 범위에 포함됐다.

개선:

- 작업 시작 전에 아래처럼 파일 소유자를 한 줄 표로 남긴다.

| 영역 | 최종 편집자 | 다른 작업자의 허용 범위 |
| --- | --- | --- |
| DB 변경 번호와 SQL | 서버 통합 담당 | 제안만 하고 직접 추가하지 않음 |
| 공통 API 계약 | 기능 통합 담당 | 도메인별 모델만 수정 |
| ADR 인덱스와 CHANGELOG | 마지막 통합 담당 | 개별 ADR 본문만 수정 |
| 공통 테스트 도우미 | 프런트 통합 담당 | 기능 테스트에서 사용만 함 |

- 서로 다른 기능이 같은 공통 파일을 만질 예정이면 병렬로 구현하지 않고, 공통 기반을 먼저 한 커밋으로 확정한다.
- DB 변경 번호는 작업 시작 시 예약하고 파일 해시가 같은지도 확인한다.

### 3.3 통합 확인이 너무 뒤에 몰렸다

각 하위 작업은 focused test에서 충분히 확인됐지만, 최신 `main`과 합친 상태는 마지막에야 본격적으로 검증됐다. 그 결과 파일 분리 방식, 빈 구성, 메서드 목록처럼 “합쳤을 때만 생기는 문제”가 머지 직전에 한꺼번에 나타났다.

문제점:

- 큰 충돌을 해결하면서 기능 의미까지 동시에 판단해야 했다.
- 컴파일, 정적 검사, 단위 테스트 실패가 순서대로 드러나 수정 횟수가 늘었다.
- 최종 단계에서 변경량이 커져 리뷰 집중도가 떨어질 수 있었다.

개선:

- 기능 묶음이 끝날 때마다 최신 `main`을 가져온 통합 전용 브랜치에서 최소한 다음을 확인한다.

  1. 양쪽 코드 컴파일
  2. 공통 API 타입 검사
  3. DB 변경 번호와 내용 충돌
  4. 아키텍처 인벤토리
  5. 충돌 파일의 focused test

- 실제 `main` 머지는 마지막에 한 번만 하되, 같은 모양의 “연습 통합”을 앞에서 수행한다.

### 3.4 검증은 많았지만 결과 재사용 방식이 약했다

개별 작업 보고서에는 테스트 명령과 통과 개수가 자세히 기록됐다. 하지만 기록이 파일별 보고서에 흩어져 있어, 뒤 작업에서 어떤 결과를 그대로 믿어도 되는지 빠르게 판단하기 어려웠다.

문제점:

- 코드가 바뀌지 않은 영역도 전체 검사를 다시 실행했다.
- 반대로 aggregate test의 알려진 실패는 여러 보고서에서 반복 설명됐다.
- 검증 수가 많아질수록 “무엇이 마지막으로 유효한 결과인지” 찾기 어려워졌다.

개선:

- 검증 결과를 아래 네 값으로 한곳에 기록한다.

| 항목 | 뜻 |
| --- | --- |
| 커밋 | 어떤 코드에서 실행했는지 |
| 영향 범위 | 실제로 바뀐 파일·계약 |
| 명령과 결과 | 실행한 검사와 통과·실패 |
| 재사용 조건 | 어떤 파일이 바뀌면 다시 실행해야 하는지 |

- 같은 커밋이고 영향 범위의 파일 해시가 같으면 기존 통과 결과를 재사용한다.
- 전체 검사는 기능 브랜치 확정 시 1회, 머지 해결 과정에서 공통 코드가 바뀐 경우에만 머지 상태에서 1회 실행한다.
- 전체 검사가 실패하면 곧바로 전체를 반복하지 않는다. 실패 묶음을 단독 실행해 실제 회귀인지 먼저 구분한다.

### 3.5 리뷰와 검증의 역할이 섞였다

일부 라운드에서는 리뷰가 새 제품 요구, 동시성 증명 확대, 모든 변형의 추가 테스트를 함께 요구했다. 이 중 일부는 안전에 의미가 있었지만, 일부는 완성 조건을 계속 움직이게 만들었다.

개선:

- 리뷰 결과를 즉시 세 칸으로 나눈다.

| 분류 | 처리 |
| --- | --- |
| 지금 고쳐야 함 | 실제 잘못된 동작, 보안·데이터·동시성 위험, 깨진 빌드 |
| 이번 변경 확인 | 변경된 파일의 테스트나 계약 확인 |
| 다음 작업 후보 | 낮은 가능성, 더 넓은 변형, 운영 환경에서만 측정 가능 |

- 독립 리뷰는 최종 통합 전에 1회 수행한다.
- 리뷰 수정 뒤에는 리뷰가 지적한 영향 범위만 다시 확인한다. 새 중요 회귀가 아니면 리뷰 라운드를 다시 열지 않는다.

### 3.6 E2E 테스트 도우미가 새 화면과 함께 바뀌지 않았다

새 모임 화면이 기존 editor 중심 구조를 folio workspace로 바꿨지만, 일부 오래된 E2E 도우미와 선택자는 뒤늦게 맞춰졌다.

문제점:

- 실제 제품 결함과 오래된 테스트 기대값을 구분하는 시간이 필요했다.
- 기능 구현이 끝난 뒤 legacy E2E 정리가 별도 커밋으로 몰렸다.

개선:

- 화면의 이름, 주소, 주요 버튼이 바뀌는 작업은 E2E 도우미 수정까지 같은 작업으로 묶는다.
- 선택자는 화면 배치나 문구 전체보다 역할과 안정된 `data-testid`를 우선한다.
- 기존 주소 호환 테스트와 새 canonical 주소 테스트를 분리해, 어느 계약이 깨졌는지 바로 보이게 한다.

### 3.7 아키텍처 검사가 파일 구조에 너무 민감했다

세션 조회를 여러 파일로 나눈 뒤에도 동작 규칙은 같았지만, 아키텍처 검사는 특정 파일명과 일반 함수 선언 모양을 기준으로 허용 여부를 판단했다. 확장 함수로 분리된 안전한 잠금 조회가 위반으로 잡혔다.

개선:

- “어느 파일에 있는가”보다 “삭제된 모임을 제외하는 조건과 잠금이 있는가”를 검사한다.
- 꼭 허용 목록이 필요하면 함수명, 안전 조건, 사용 이유를 함께 기록한다.
- 쿼리 파일을 분리하는 리팩터링은 아키텍처 검사도 같은 커밋에서 갱신한다.

### 3.8 테스트 격리가 완전하지 않았다

이번 과정에서 공개 익명화 fixture 오염, 이미지 투명 픽셀 polling, AI 스케줄러 로그 캡처처럼 실행 순서나 시간에 민감한 신호가 보였다. 단독 재실행은 통과했지만 전체 검사 신뢰도를 낮춘다.

개선:

- 테스트마다 자신이 만든 DB·캐시·로그 상태를 직접 정리한다.
- 시간이나 polling에 의존하는 테스트는 가능한 한 가짜 시계와 직접 완료 신호를 사용한다.
- 일시 실패는 다음 형식으로 남긴다: `전체 실행 실패 → 단독 재현 결과 → 변경 범위 관련성 → blocker 여부`.
- 단독 실행에서 통과했다고 무조건 무시하지 않는다. 같은 테스트가 두 번 이상 흔들리면 별도 안정화 작업으로 올린다.

### 3.9 기존 `main` 문서 변경 복원이 추가 위험을 만들었다

작업 전부터 `main`에 사용자가 수정 중인 문서가 있었다. 머지를 위해 임시 보관한 뒤 다시 적용했지만, ADR 인덱스 두 곳에서 충돌이 발생했다. 원본은 stash에 보존됐지만, 마지막 단계의 판단 비용이 늘었다.

개선:

- 시작할 때 기존 변경 파일 목록을 저장하고 작업 파일과 겹치는지 확인한다.
- 겹치는 문서는 통합 담당자 한 명만 편집한다.
- 복원할 때는 원본 보관 위치, 자동 적용된 파일, 수동 해결한 파일, 스테이징 여부를 각각 확인한다.
- 사용자의 기존 변경은 기능 커밋에 섞지 않는다.

## 4. 잘된 점과 유지할 방식

모든 과정이 비효율적이었던 것은 아니다. 다음 방식은 계속 유지할 가치가 있다.

- 별도 worktree를 사용해 기능 브랜치와 사용자의 `main` 변경을 분리했다.
- target drift, 잠금 순서, lifecycle 경쟁처럼 실제 데이터 안전에 영향을 주는 문제는 끝까지 닫았다.
- 마지막에는 위험 기준을 명확히 바꿔 낮은 가능성의 증명 확대를 머지 blocker로 만들지 않았다.
- 전체 실패를 바로 코드 결함으로 단정하지 않고 단독 재현으로 테스트 흔들림을 구분했다.
- 공개 릴리스 후보와 secret scan을 머지 전에 확인했다.
- 사용자 문서는 별도 stash로 보존했고 기능 머지 커밋에 포함하지 않았다.

## 5. 다음 작업의 권장 진행 순서

### 시작할 때

1. `git status`와 모든 worktree 상태를 기록한다.
2. 기능 범위, 제외 범위, 반드시 닫을 위험을 한 화면에 적는다.
3. 병렬 작업의 파일 소유자 표를 만든다.
4. DB 변경 번호와 공통 API 계약 담당자를 정한다.
5. 기존 사용자 변경 파일과 복원 방법을 기록한다.

### 각 작업 단위가 끝날 때

1. 실제 변경 파일을 확정한다.
2. 그 파일에 직접 연결된 focused test를 실행한다.
3. 검증 결과를 커밋 해시와 함께 기록한다.
4. `DONE_WITH_CONCERNS`라면 남은 항목의 담당 작업과 blocker 여부를 반드시 적는다.
5. 두 개 이상의 작업이 같은 공통 파일을 건드렸다면 즉시 연습 통합을 한다.

### 최종 통합 전에

1. 최신 `main`과 연습 통합한다.
2. DB 변경 파일의 번호와 내용을 비교한다.
3. 공통 API와 테스트 빈 구성을 컴파일한다.
4. 독립 리뷰를 1회 수행한다.
5. 리뷰 결과를 `지금 수정 / 변경 확인 / 다음 작업`으로 나눈다.
6. 지금 수정 항목만 닫고 변경 영향 범위만 재검증한다.

### 머지할 때

1. 기능 브랜치의 마지막 검증 커밋을 확정한다.
2. `main`에서 연습 통합과 같은 방식으로 머지한다.
3. 충돌 해결로 코드가 바뀐 영역만 focused test한 뒤 필요한 canonical gate를 실행한다.
4. 공개 릴리스 검사와 `git diff --check`를 실행한다.
5. 사용자 변경을 복원하고 staged·unstaged·unmerged 상태를 각각 확인한다.
6. 머지 커밋, 기능 커밋, 남은 위험, 실행하지 않은 검증을 함께 기록한다.

## 6. 반복을 멈추는 기준

다음 중 하나면 새 수정 라운드를 연다.

- 개인정보가 노출될 수 있다.
- 데이터가 사라지거나 잘못 섞일 수 있다.
- 실제 교착 상태가 재현된다.
- 인증이나 권한 검사를 우회할 수 있다.
- 현재 변경 때문에 빌드나 필수 테스트가 실패한다.
- 사용자의 핵심 작업 흐름이 실제로 완료되지 않는다.

다음은 기본적으로 `남은 위험`에 기록하고 머지를 막지 않는다.

- 모든 인증 변형을 조합한 추가 경쟁 테스트
- 이미 확인한 규칙의 형식적 증명 확대
- 운영 환경에서 오랜 시간 관찰해야 하는 낮은 가능성의 공백
- 변경하지 않은 영역의 일회성 테스트 흔들림
- 수동 접근성 검증처럼 별도 환경과 사람이 필요한 확인

단, 같은 일시 실패가 반복되거나 사용자 데이터·권한과 연결되면 즉시 blocker로 다시 분류한다.

## 7. 바로 복사해 쓰는 체크리스트

```text
[시작]
- 현재 branch/worktree/dirty file 기록
- 이번 작업의 포함/제외 범위 기록
- 파일 소유자와 DB 변경 번호 예약
- Critical/Important 종료 기준 합의

[작업 단위]
- 변경 파일 확정
- focused test 통과
- 검증 커밋 해시 기록
- 남은 concern의 담당 작업과 blocker 여부 기록

[통합]
- 최신 main 연습 통합
- DB 변경 번호/내용 비교
- 공통 API compile
- 독립 리뷰 1회
- 중요 항목만 수정
- 다시 바뀐 범위만 재검증

[머지]
- 기능 HEAD 확정
- main 머지
- 충돌 영향 범위 검사
- canonical gate와 공개 릴리스 검사
- 사용자 변경 복원
- staged / unstaged / unmerged 상태 확인
- 머지 hash와 residual risk 기록
```

## 8. 다음 작업에서 확인할 개선 지표

다음 회고에서는 테스트 개수보다 아래 항목을 먼저 본다.

- 세 번째 이상 수정 라운드가 시작되기 전에 범위를 다시 판단했는가?
- 같은 공통 파일을 여러 병렬 작업이 동시에 수정하지 않았는가?
- DB 변경 번호 충돌을 구현 초기에 발견했는가?
- 전체 검사를 코드 변경 없이 반복하지 않았는가?
- `DONE_WITH_CONCERNS` 항목이 담당자 없이 다음 단계로 넘어가지 않았는가?
- 최종 머지에서 처음 발견된 계약 충돌이 줄었는가?
- 사용자 기존 변경을 정확히 보존하고 기능 커밋과 분리했는가?

목표는 검증을 줄이는 것이 아니다. **실제 위험을 더 빨리 찾고, 같은 근거를 반복해서 만드는 시간을 줄이는 것**이다.
