# ReadMates 플랫폼 운영 화면 사이트 톤 재설계

작성일: 2026-08-12
상태: APPROVED DESIGN SPEC
구현 상태: 시작 전
대상 표면: `front/`의 플랫폼 관리자 셸과 `/admin/today`

## 1. 배경

현재 `/admin/today`는 단순 목업이 아니다. 서버에 저장되는 운영 케이스, 필터와 페이지네이션,
주기적 갱신, 낙관적 동시성 제어, 조치 기록, 모바일 목록·상세 흐름을 이미 제공한다. 다만 화면의
정보 구조와 시각적 위계가 이 기능을 충분히 드러내지 못해 실제 운영 제품보다 데모 화면처럼 보인다.

이번 재설계는 기능을 새로 발명하기보다 현재 계약을 운영자가 빠르게 읽고 안전하게 조치할 수 있는
작업대로 다시 구성한다. 동시에 공개 사이트에서 사용 중인 ReadMates의 차분한 편집 디자인을 관리자
화면에도 이어, 서로 다른 제품처럼 보이는 간극을 없앤다.

구조를 ReadMates의 언어와 기존 계약으로 번역한다.

## 3. 목표

1. 운영자가 첫 화면에서 무엇을 먼저 봐야 하는지 5초 안에 파악할 수 있다.
2. 심각도, 상태, 범위, 영향, 경과 시간을 배지 해독 없이 한 행에서 비교할 수 있다.
3. 근거 확인, 담당 확인, 보류, 해결의 차이를 분명히 하여 잘못된 상태 전이를 줄인다.
4. 데스크톱에서는 목록의 맥락을 잃지 않고 상세를 확인하며, 모바일에서는 한 손으로 한 단계씩
   완료할 수 있다.
5. 공개 사이트와 같은 타이포그래피, 색, 선, 여백의 문법을 사용하되 운영 화면에 필요한 밀도를
   유지한다.
6. 기존 API, 권한, 동시성, 케이스 이력 계약을 보존한다.

## 4. 비목표

- 서버 API, 데이터베이스 스키마, Flyway migration을 새로 만들지 않는다.
- 범용 실행 엔진이나 일괄 조치 기능을 추가하지 않는다.
- 저장된 사용자 정의 뷰, 명령 팔레트, 대시보드 차트, KPI 카드를 추가하지 않는다.
- `/admin/**` 전체를 한 번에 재설계하지 않는다.
- 관리자 권한의 의미나 `PLATFORM_ADMIN`·`SUPPORT`의 허용 범위를 바꾸지 않는다.
- 실제 클럽 이름을 추측하거나 샘플 운영 데이터를 제품 코드에 넣지 않는다.
- 그라데이션, 글래스 효과, 과도한 그림자, 종이 질감, 서재 장식, 카페 감성을 사용하지 않는다.

## 5. 선택한 접근

선택한 접근은 **ReadMates 운영 기록대**다.

```text
사이트와 연결된 조용한 관리자 셸
  -> 오늘의 상태를 한 문장과 한 줄로 요약
  -> 빠른 작업 관점과 검색·필터
  -> 번호가 있는 고밀도 운영 기록 목록
  -> 선택한 기록의 근거·이력·안전한 조치
```

비교한 대안은 다음과 같다.

### 5.1 대안 A — SaaS 모니터링 대시보드

카드, 차트, 색상 배지로 상태를 요약하는 방식이다. 시스템 건강을 한눈에 보는 데 유리하지만 현재
ReadMates 운영자의 핵심 과업인 개별 사건의 확인과 조치를 화면 아래로 밀어낸다. 공개 사이트의
편집 톤과도 거리가 커 선택하지 않는다.

### 5.2 대안 B — 커뮤니티 운영 인박스

메시지 인박스처럼 부드럽고 친숙하지만 사건의 심각도, 출처, 범위, 버전 충돌을 충분히 드러내기
어렵다. 지원 화면에는 어울릴 수 있으나 플랫폼 운영의 단일 기준으로는 정보 밀도가 부족하다.

### 5.3 선택안 C — 운영 기록대

목록의 비교 가능성과 감사 기록의 신뢰성을 중심에 두고 ReadMates의 편집 디자인을 입힌다. 상태는
차분하게 보이되 긴급도와 주된 다음 행동은 명확하다. 현재 데이터 계약을 그대로 활용할 수 있고
데스크톱·모바일 모두 일관된 작업 흐름을 만들 수 있어 선택한다.

## 6. 시각 언어

### 6.1 브랜드 연결

- 왼쪽 위에는 공개 사이트와 같은 파란 책 모양 마크와 `읽는사이` 워드마크를 사용한다.
- 제품 영역명 `플랫폼 운영`은 브랜드보다 한 단계 낮은 크기와 무게로 표시한다.
- 배경은 따뜻한 아이보리, 본문은 짙은 먹색, 주요 선택과 링크는 절제된 네이비를 사용한다.
- 위험색은 실제 긴급·실패·파괴적 조치에만 둔한 적갈색으로 제한한다.
- 굵은 한국어 산세리프 제목, 읽기 편한 본문, 얇은 가로선의 리듬을 유지한다.

### 6.2 밀도와 위계

- 카드 여러 장보다 한 화면의 연속된 기록면을 우선한다.
- 표면을 구분할 때 큰 그림자 대신 1px 선, 배경 명도 차, 여백을 사용한다.
- 제목, 요약 문장, 상태 원장, 빠른 관점, 필터, 목록, 상세 순으로 시선이 내려간다.
- 배지는 상태를 반복 장식하지 않는다. 색만 보아도 의미가 통하도록 만들지 않고 항상 텍스트를
  함께 둔다.
- 숫자는 비교할 때만 고정폭 숫자 스타일을 사용한다.

### 6.3 금지 패턴

- 모든 값을 둥근 pill로 감싸지 않는다.
- 장식 목적의 대형 빈 영역이나 영웅 이미지를 두지 않는다.
- 운영 사건을 분석 차트나 점수 하나로 축약하지 않는다.
- 긴급도를 행 전체의 강한 배경색으로 표현하지 않는다.
- 실제 책, 종이 더미, 스탬프 같은 사물을 문자 그대로 묘사하지 않는다.

## 7. 관리자 셸

### 7.1 상단 헤더

상단은 얇고 고정된 제품 헤더다.

- 왼쪽: `읽는사이` 브랜드, 구분선, `플랫폼 운영`
- 가운데 또는 본문 시작점: `지휘대 / 오늘` breadcrumb
- 오른쪽: 현재 플랫폼 역할과 작업 공간 메뉴
- 전역 `새 클럽` 버튼은 모든 관리자 라우트에서 제거하고 클럽 페이지 헤더의 문맥 행동으로 옮긴다.

### 7.2 사이드바

탐색은 한국어 우선이며 기능 소유권에 따라 세 묶음으로 나눈다.

```text
지휘대
  오늘
  클럽

운영
  사건
  알림
  AI 작업
  지원

기록
  감사
  분석
```

현재 위치는 좌측 강조선, 텍스트 무게, 낮은 명도 배경으로 표현한다. 아이콘만으로 의미를 전달하지
않는다. 넓은 화면에서는 항상 보이고, 중간 화면에서는 축소 가능하며, 모바일에서는 메뉴 버튼으로
여는 modal drawer가 된다.

## 8. `/admin/today` 데스크톱 구조

### 8.1 페이지 도입부

- 제목: `오늘의 운영`
- 보조 문장: `먼저 확인할 일 2건이 있습니다.`
- 상태 원장: `활성 7 · 긴급 2 · 내 담당 3 · 보류 2 · 10:42 기준`
- 원천 상태: `전체 신호 정상`

숫자는 현재 응답으로 계산하고 하드코딩하지 않는다. 원천 상태가 일부 실패하면 정상처럼 보이게
합치지 않고 실패한 원천과 마지막 정상 시각을 구체적으로 표시한다.

### 8.2 빠른 작업 관점

카드 대신 밑줄 탭을 사용한다.

- `처리 필요 7`
- `내가 확인함 3`
- `보류 2`
- `오늘 해결 4`

탭은 URL로 표현 가능한 기존 필터 조합의 별칭이다. 새 서버 개념을 만들지 않는다. 현재 탭은 색과
밑줄뿐 아니라 `aria-current` 또는 동등한 상태로 전달한다.

### 8.3 검색과 필터

- 하나의 검색 입력
- 빠른 토글 `내 담당`
- 필터 메뉴 버튼 `필터 2`
- 적용 중인 필터 chip과 `초기화`

필터 수는 실제 적용 조건 수를 반영한다. 메뉴는 키보드로 열고 이동하고 닫을 수 있으며, Escape로
닫힌 뒤 트리거로 초점이 돌아간다. 검색과 필터 변경은 URL 상태와 동기화한다.

### 8.4 작업 영역

폭 1180px 이상에서는 목록과 상세를 나란히 둔다.

```text
┌──────────────────────────┬──────────────────────┐
│ 운영 기록 목록           │ 선택한 기록 · 07     │
│ 07  긴급 사건 ...        │ 핵심 사실             │
│ 06  확인 필요 ...        │ 개요/변경 기록/근거    │
│ 05  보류 ...             │ 조치                   │
└──────────────────────────┴──────────────────────┘
```

- 목록은 남은 폭의 주 표면이며 상세 패널은 읽기 가능한 고정 범위 너비를 가진다.
- 선택 행은 배경, 왼쪽 선, `aria-selected`를 함께 사용한다.
- 상세 패널은 페이지 스크롤 안에서 sticky가 될 수 있으나 상단 헤더와 충돌하지 않는다.
- 목록과 상세를 별도 카드 더미로 만들지 않고 하나의 기록면처럼 연결한다.

## 9. 운영 목록

각 행은 얇은 선으로 구분된 두 줄 구조다.

첫째 줄:

- 짧은 위치 번호
- 심각도
- 사건 제목
- 상태

둘째 줄:

- 출처
- 클럽 또는 플랫폼 범위
- 영향
- 마지막 관측 또는 경과 시간
- 담당 상태

### 9.1 짧은 번호 계약

시안의 `07`, `06`은 영구 식별자가 아니라 **현재 작업 관점 안의 위치 표시자**다.

- API와 URL의 실제 식별자는 기존 UUID를 계속 사용한다.
- 짧은 번호는 링크, 복사값, 로그, 접근성 이름에서 사건의 식별자로 사용하지 않는다.
- 처음 불러온 7개 행은 위에서부터 `07`에서 `01`까지 내려가도록 표시한다.
- 운영자가 사건을 읽는 동안 백그라운드 갱신으로 행 순서와 번호를 바꾸지 않는다.
- 새 사건이 들어오면 `새 케이스 1건` 알림을 표시하고 운영자가 갱신을 선택할 때 목록을 다시 정렬한다.
- 명시적 갱신, 빠른 관점 변경, 필터나 정렬 변경 시 현재 결과 집합을 기준으로 번호를 다시 계산한다.
- 선택한 사건은 UUID로 추적하므로 번호 재계산 뒤에도 같은 사건이 선택된다.

이 계약은 짧은 번호를 기억하기 쉽게 보이게 하면서 영구 ID로 오해하거나 새 데이터 때문에 작업 위치가
갑자기 바뀌는 문제를 피한다.

### 9.2 클럽 표시명

현재 관리자 클럽 query가 이미 불러온 데이터에서 `clubId`를 표시명으로 매핑한다. 새 endpoint를
추가하지 않는다. 매핑 데이터가 없거나 불러오기 실패 시 이름을 추측하지 않고 `클럽 범위`로
표시하며 상세에서 원본 범위 식별 정보를 안전한 형식으로 제공한다.

## 10. 선택한 기록 상세

상단은 `선택한 기록 · 07`로 현재 위치를 보여주되 실제 사건의 제목과 상태가 더 높은 의미를 갖는다.

### 10.1 핵심 사실

- 심각도와 현재 상태
- 처음·마지막 관측 시각
- 출처와 범위
- 영향 설명
- 담당 상태
- 마지막 성공적으로 확인한 데이터 시각

### 10.2 섹션 탭

- `개요`: 운영자가 지금 판단할 핵심 사실과 권장 다음 단계
- `변경 기록`: 행위자, 시각, 행동, 결과 순의 감사 timeline
- `근거`: 출처별 원문 맥락, 관련 위치, 원천 freshness

탭을 바꿔도 선택한 사건과 목록 위치는 유지한다.

### 10.3 행동 위계

1. 주 행동: `원인과 영향 보기`
2. 보조 행동: `내가 확인`
3. 추가 행동 메뉴: `보류…`, 조건을 만족할 때 `해결`

정보 확인을 상태 변경보다 앞에 둔다. `보류…`는 기간 또는 사유를 받는 dialog를 열며 저장 전
확인할 수 있다. `해결`은 현재 신호와 허용 행동을 다시 확인한 뒤에만 노출한다. 위험한 조치와 단순
탐색은 같은 시각 무게를 갖지 않는다.

`SUPPORT`는 같은 근거를 볼 수 있지만 허용되지 않은 조치 대신 읽기 전용 이유를 구체적으로 본다.

## 11. 반응형 동작

### 11.1 넓은 화면 — 1180px 이상

- 고정 사이드바
- 목록과 persistent inspector의 분할 화면
- 현재 선택과 상세 탭을 동시에 확인

### 11.2 중간 화면 — 768px 이상 1179px 이하

- 축소 가능한 탐색
- 목록에서 사건을 선택하면 같은 작업 영역의 단일 상세 화면으로 이동
- 목록과 상세를 세로로 쌓지 않는다.
- 상세의 `운영 목록`으로 돌아가면 필터, 스크롤, 선택이 복원된다.

### 11.3 모바일 — 767px 이하

- 공개 사이트와 이어지는 compact header와 메뉴 drawer
- 첫 viewport는 장식 없이 현재 상태와 실제 작업 목록에서 시작
- 목록 행은 `07`, 핵심 제목, 상태, 범위, 경과 시간, chevron을 포함한 전체 폭 touch target
- 상세는 `운영 목록` 뒤로가기, 핵심 사실, 섹션 탭, 본문, 하단 sticky action bar 순서
- sticky bar는 safe-area inset을 존중하고 본문 마지막 내용을 가리지 않는다.
- 상세 진입 시 제목으로 초점을 이동하고, 돌아올 때 이전 선택 행으로 초점을 복원한다.

## 12. 상태와 복구 설계

### 12.1 로딩과 갱신

- 최초 로딩은 실제 행 높이를 닮은 skeleton을 사용한다.
- 백그라운드 갱신 중에는 마지막 정상 데이터를 유지하고 갱신 상태만 조용히 표시한다.
- 새 사건은 목록을 즉시 흔들지 않고 명시적 새 항목 알림으로 알린다.

### 12.2 빈 상태

- 실제 빈 상태: `지금 처리할 운영 기록이 없습니다.`와 마지막 갱신 시각
- 필터 결과 없음: `현재 조건에 맞는 기록이 없습니다.`와 `필터 초기화`
- 선택한 사건이 필터에서 제외되면 다른 사건을 자동 선택하지 않는다. 상세를 비우고 제외 이유와
  `필터 초기화`를 제공한다.

### 12.3 부분 실패

- 한 원천이 실패해도 다른 원천과 마지막 정상 데이터는 유지한다.
- 실패한 원천 이름, 마지막 정상 시각, 해당 원천만 다시 시도하는 행동을 제공한다.
- `전체 신호 정상`을 표시하지 않는다.

### 12.4 조치 결과

- 확인, 보류, 해결은 각각 구체적인 성공 메시지를 사용한다.
- 일반적인 `저장되었습니다`로 상태 전이의 의미를 숨기지 않는다.
- 실패 시 입력과 선택을 보존하고 재시도할 수 있다.

### 12.5 버전 충돌

기존 version 기반 낙관적 동시성 계약을 유지한다.

1. 조치가 `409`로 거부되면 최신 사건을 다시 가져온다.
2. 무엇이 바뀌었는지 보여준다.
3. 기존 조치를 자동 반복하지 않고 운영자에게 다시 확인받는다.
4. 활성 신호가 남아 있으면 해결 상태로 표시하지 않는다.

## 13. 접근성

- 색 이외에 텍스트, 선, 아이콘, ARIA 상태를 조합해 선택·심각도·상태를 전달한다.
- 모든 행과 조치는 키보드로 접근 가능하고, 문서 순서가 시각 순서와 일치한다.
- 메뉴와 dialog는 초점 trap, Escape 닫기, 트리거 초점 복귀를 지원한다.
- 목록에서 상세로 이동한 뒤 제목에 초점을 두고, 뒤로갈 때 이전 행으로 복원한다.
- 44px 수준의 모바일 touch target과 sticky bar safe area를 확보한다.
- 자동 갱신과 새 항목 알림은 과도하게 반복 낭독하지 않는 적절한 live region을 사용한다.
- 동작 애니메이션은 짧고 기능적이며 `prefers-reduced-motion`을 존중한다.

## 14. 컴포넌트와 상태 소유권

### 14.1 `admin-shell-layout`

- 브랜드 헤더, breadcrumb, 역할 메뉴
- 데스크톱 사이드바와 모바일 drawer
- 라우트별 문맥 행동의 자리

### 14.2 `admin-today-route`

- URL 검색·필터·빠른 관점 상태
- UUID 기반 선택 상태
- polling과 마지막 정상 snapshot
- 새 사건 감지와 명시적 갱신
- 조치 mutation과 `409` 복구
- breakpoint에 따른 목록·상세 navigation state

### 14.3 operations model

- 현재 결과 집합의 짧은 위치 번호
- 빠른 관점 count와 filter alias
- 적용 filter chip과 count
- 범위·영향·경과 시간 표시 모델
- source freshness와 부분 실패 표시 모델

### 14.4 queue와 inspector

- 데스크톱과 모바일 목록은 같은 view model을 사용한다.
- inspector는 핵심 사실, 섹션 탭, 감사 timeline, 행동 위계를 렌더링한다.
- 모바일 상세는 같은 데이터와 조치 계약을 사용하고 배치만 바꾼다.

공통 디자인 token은 기존 `globals.css`의 ReadMates 체계 안에서 확장한다. 플랫폼 운영만을 위한 임의의
색상·타입 스케일을 별도 제품처럼 만들지 않는다.

## 15. 데이터 흐름

```text
URL 빠른 관점·검색·필터
  -> 기존 운영 케이스 query
      -> 표시 model: count, chip, locator, scope, time
          -> queue selection(UUID)
              -> inspector/mobile detail
                  -> ACK/SNOOZE/RESOLVE mutation(version 포함)
                      -> 성공: 현재 사건과 count 갱신
                      -> 409: 최신 사건 refetch 후 재확인

background poll
  -> 기존 결과와 UUID 비교
      -> 새 사건 없음: freshness 갱신
      -> 새 사건 있음: 현재 순서 동결 + 새 사건 알림
          -> 운영자 명시적 갱신: 정렬·번호 재계산
```

클럽 표시명은 이미 로드된 관리자 클럽 query를 `clubId`로 조회한다. 해당 query가 실패해도 운영 케이스
자체는 사용할 수 있어야 한다.

## 18. 수용 기준

- `/admin/today`가 공개 사이트와 같은 브랜드, 색, 타입, 선의 문법으로 보인다.
- 첫 viewport에서 긴급 작업, 내 담당, freshness와 실제 사건 목록을 확인할 수 있다.
- 목록 행은 심각도, 상태, 범위, 영향, 경과 시간을 두 줄 안에서 비교할 수 있다.
- 짧은 번호는 현재 view locator로만 동작하며 실제 UUID 계약을 바꾸지 않는다.
- 백그라운드 새 사건이 현재 읽기 위치를 바꾸지 않고 명시적 갱신 뒤에만 재정렬된다.
- 데스크톱은 목록·상세를 함께, 중간 화면과 모바일은 목록→상세 단계로 제공한다.
- 필터·스크롤·선택·초점이 상세 왕복 뒤 복원된다.
- 부분 실패, 실제 빈 상태, 필터 빈 상태, 조치 실패, `409` 충돌이 서로 다른 복구 경로를 가진다.
- `SUPPORT`가 허용되지 않은 조치를 실행할 수 없고 그 이유를 이해할 수 있다.
- 새 서버 endpoint, migration, 실제 운영 데이터, 새 권한 의미를 도입하지 않는다.
